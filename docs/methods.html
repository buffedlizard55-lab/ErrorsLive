Methods & audit

Every displayed result is derived by code from either an official MLB feed, the documented NY Daily News archive, or a committed fixture clearly labelled as historical. The audit suite recomputes published metrics and checks claims on every push; snapshots and network reachability are explicitly timestamped and may be stale when an endpoint or scheduled job fails.

The pipeline

1 · Ingest (needs network → runs in CI)

tools/ingest_official.py walks /api/v1/schedule day by day, fetches each game's feed/live with a trimmed fields list, and re-checks every game's final score against /api/v1/game/{pk}/linescore. A mismatch is recorded, never repaired.

The historical ingest runs in .github/workflows/ingest.yml. Separate scheduled jobs refresh the static live fallback (live-refresh.yml) and observe ruling changes (ruling-watch.yml). The live page also attempts direct browser reads of the public schedule and game-feed endpoints; browser access is tested separately and falls back to the committed snapshot on failure. Reports and failure status are committed instead of silently substituting data.

2 · Rebuild (offline, byte-reproducible)

python3 tools/run_all.py rebuilds offline-derived artifacts from committed sources: the audit sample, fitted model, NYDN archive and labelled historical live fixture. The live official snapshot is a separate network artifact and is not rewritten by the offline rebuild. CI runs it and fails the build if git diff is not empty — i.e. if the committed artifacts are not exactly what the code produces.

python3 tests/test_pipeline.py then recomputes the published numbers again, independently, from the raw data.

Labels, and what is never invented

  • The model target is the latest captured official feed's final result.eventType, mapped to hit / error / fielder's choice / out. It is not an initial-call history, and nothing is imputed or hand-edited.
  • The live feed state no_event_type_yet means contact hitData exists while result.eventType is absent. MLB does not expose its scorer queue; this is not proof that an official ruling is pending.
  • Batted balls with no complete Statcast vector are quarantined, not filled in: the count is published in data/data_quality.json and in the model's honesty block.
  • Two run-impact diagnostics are published for reviewed plays: a runner-movement/scoreboard consistency check (legacy field name run_removed_hard; not proof of a run removal) and a labelled heuristic for selected overturned reviews. The reason is stored on each flagged row; heuristic candidates are not manually confirmed.
  • MLB's two-letter reviewType codes (MJ, MA, …) are stored verbatim and never translated by guesswork. Where a human-readable subject is needed the site uses the feed's own play text — e.g. “Marlins challenged (tag play), call on the field was overturned: …”.
  • Archived 2014–18 video short-links are resolved and the result recorded (status code and final URL) instead of being presented as working links.

Validation design

  • GroupKFold by game is the published cross-validation. StandardScaler is fitted inside each training fold. Stratified random folds are a comparator only: neither score is assumed to bound the other.
  • Group bootstrap (whole games resampled) gives the intervals, because games — not plays — are the independent unit here.
  • Model-free surface (trajectory × exit-velocity error rates with Wilson intervals) is published so the key relationship can be checked without trusting any model.
  • The RBI stake is measured, not asserted. The brief's RBI question is a question about the official statistic, so tools/rbi_evidence.py tabulates the feed's own result.rbi by final call and by base/out state, with Wilson intervals, and lists every error-ruled play in the window that still earned an RBI — each with its play id and official feed URL. That table is published on RBI stakes, measured from docs/data/rbi_evidence.json, and the audit suite recomputes every cell from docs/data/bip_official.csv. The same script quotes Rule 9.04 verbatim from the rule text already published on Rules & RBI, and a check asserts the two copies of the quotation are identical.
  • Calibration is shown bin by bin from grouped out-of-fold predictions. The isotonic Brier check uses nested GroupKFold: inner-fold predictions fit the calibrator, and each outer game fold is held out from both base-model fitting and calibration evaluation.
  • The audit suite re-derives the model from the dataset the model declares it used, so a stale page fails CI instead of quietly misleading a reader.

Known limitations (kept current, not buried)

  • The model sees contact physics and limited pre-pitch context only. Fielder positioning, hang time, park, weather and scorer identity are not inputs. Its target is the latest final feed label, not the probability of a future reclassification.
  • In grouped out-of-fold evaluation, the model does not nominate error as the most likely class. The /100 score is therefore a ranking/triage aid, not a decision or an overturn probability.
  • The model sample spans 590 games from 2026-08-15 through 2026-09-27. It does not establish performance on a full season, another year, or an unseen scorer/park environment.
  • The ruling watcher polls live games every 15 minutes and rechecks recent final games daily. It can miss a short-lived feed state between polls; it cannot see an MLB internal pending queue.
  • Official review data in modern feeds mixes replay reviews with automated pitch-result challenges; both are kept, labelled with is_pitch_challenge, and counted separately.
  • Raw feeds are not committed for the ingested window (they are hundreds of megabytes). What is committed is the derived CSVs plus data/ingest/games.csv, which carries the exact official URL for every game so any row can be re-verified by anyone with network access.
  • Video: the per-play watch link is Baseball Savant's own player page for the league's playId. Direct .mp4 renditions are attached only when the official content endpoint exposes one for that exact play id.

Observing scoring changes — not an official pending queue

tools/watch_rulings.py captures active feeds every 15 minutes and re-reads the recent live/final window daily. When hitData is present but result.eventType is absent, it records no_event_type_yet; later changes to event type, RBI, description or review metadata are appended to data/ingest/ruling_changes.csv. The record includes whether the first captured state already had an eventType, contact/context fields, timestamps, the official feed, and MLB's scoring-changes page. A difference between snapshots proves only that the feed values changed between those observations. It does not prove when or why the scorer made a decision. Zero logged changes is not proof that no changes occurred.

Loading data/ruling_changes.json…

RBI notes are conditional. MLB's error glossary summarizes the ordinary treatment of error-dependent runs; Rule 9.04 contains the controlling exceptions, and the 2026 text of subsection (a)(3) is now reproduced verbatim on Rules & RBI (page 115 of the official PDF): before two are out, an error on a play where a runner from third base ordinarily would score still credits the batter with an RBI. The feed row is still not a ruling — the scorer's judgment is.

Live alerts — the browser half of the watcher

Live alerts polls the official schedule and game feeds in your browser and diffs each poll against the previous one with docs/alerts.js. That module is deliberately pure — no DOM, no timers, no network — so tests/test_pipeline.py runs it under node and proves the alert rules: a pending feed row that gains an eventType raises decision_settled; an eventType that changes raises event_type_changed (this is the error → hit / fielder's-choice case); an rbi field that moves raises rbi_changed; the same transition is never alerted twice; and a first poll only establishes a baseline so opening the page does not fire hundreds of alerts. When the browser cannot reach statsapi.mlb.com, the page falls back to the CI ledger in docs/data/alerts.json, which is rebuilt by tools/build_site_data.py from data/ingest/ruling_changes.csv and the flagged reviews — never from hand-typed rows.

A watcher defect was found and fixed in this review. The scheduled watcher's status file (data/ingest/ruling_watch_status.json) reported ok: false with TypeError: 'int' object is not subscriptable. Cause: the diff compared values loaded from the snapshot CSV (all text) against freshly parsed API values (integers) for reviewed, overturned and rbi, so an unchanged play looked changed and the ledger then sliced an integer. The comparison now normalises both sides, the diff is a pure function with an offline regression test, and the change ledger can populate again. Two further defects showed up the moment the watcher first ran successfully, and both are fixed as well. (1) The stored snapshot predated the status column, so every row read back as an empty string and its first re-observation was recorded as '' → 'scored': 12,349 rows of pure format noise were published as changes. The comparison now covers only the fields the stored snapshot actually carries a column for, and an empty previous value for a derived field (status, reviewed, overturned) is treated as unknown rather than as an observation. The 12,349 artifact rows were removed from data/ingest/ruling_changes.csv; the untouched raw file is preserved in git commit e81bb25 and the removal is documented in data/ingest/ruling_changes_cleaning.json. (2) The collector appended a fresh copy of every play on each capture, so the pre-fix snapshot held 24,751 rows for 12,349 plays: 12,402 of those rows were duplicates — 12,349 re-captures of plays already stored, plus 53 rows for a single game (824785) that the schedule endpoint lists under two dates because it ran past midnight. The schedule is now de-duplicated by gamePk at its official date, and stored rows are de-duplicated by (game_pk, at_bat) before comparison. With both fixes the same window reports 0 changes, and the ledger holds its first real observations: 1,107 field differences between two captures of the official feed (reviewed 0→1 ×426, review_type appearing ×426, overturned 0→1 ×255), the count the cleaning record was written against. The ledger keeps growing — the next scheduled capture added one description difference (game 849843, at-bat 4, 2026-09-30T05:28:01Z) — so that count is a floor, and the audit checks the record against the ledger as it stood at its own cleaned_utc rather than against the live total. A difference is evidence that the captured field changed between two observations — the feed can also backfill metadata — so every published row carries its official feed URL for verification.
